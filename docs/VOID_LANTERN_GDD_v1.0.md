# VOID LANTERN
## Game Design Document & Implementation Specification

**Версия:** 1.0 · **Статус:** исходная спецификация для разработки · **Язык игры:** English (en-US), готовность к локализации ru-RU

**Жанр:** горизонтальный 2D shoot ’em up / arcade side-scroller. **Режим:** один игрок, offline. **Платформы:** Linux x86-64, Windows x86-64. **Движок:** Godot 4.x (минимум 4.5), GDScript. **Целевая частота:** 60 FPS. **Возрастная направленность:** подростки и взрослые; стилизованный космический ужас без натуралистичной жестокости.

> Это самостоятельная игра, вдохновлённая принципами R-Type: принудительный скроллинг, позиционные задачи, заряжаемое оружие, отделяемый модуль и крупные многофазные боссы. Название, сюжет, корабли, спрайты, музыка, карты, противники и паттерны должны быть оригинальными. Не переносить ROM, оригинальные ресурсы, имена персонажей, музыку и точную геометрию уровней R-Type. VOID LANTERN — рабочее название, не проверенное на товарные знаки.

---

## Навигация

# 0. Контракт для coding-агента

Документ является исходной проектной спецификацией. Все числовые параметры являются стартовым нормативом, а не измеренным результатом плейтестов. Изменения допустимы после воспроизводимого теста, если они зафиксированы в `docs/BALANCE_CHANGES.md`. Не заменять механики упрощёнными заглушками без явного согласования.

- Разработать полноценную игру, а не демонстрацию движка, редактор уровней или набор статичных экранов.
- Вначале завершить вертикальный срез: меню → первый уровень целиком → босс → экран результата → повтор/переход. Затем создавать остальные уровни на той же архитектуре.
- Все восемь уровней должны иметь уникальную геометрию, декор, темп, сценарий волн, музыку и босса. Реиспользовать движок, а не один уровень с перекрашенными спрайтами.
- В репозитории должны быть исходники всех собственных графических и аудиоресурсов или детерминированные генераторы этих ресурсов, а также реестр лицензий. Игра запускается без доступа к сети, ключей API и платных ассетов.
- Не использовать изображения с водяными знаками, чужие саундтреки, шрифты без лицензии, бесконечный случайный спавн вместо сценариев, текстовые прямоугольники вместо финальных спрайтов.
- Каждый этап: проверить запуск, автоматизированные тесты, ручной игровой проход, зафиксировать команды, наблюдения и известные ограничения. Не объявлять тест выполненным, если он фактически не запускался.
- Если движок недоступен в окружении, не симулировать результат: сохранить готовый код и явно указать, какие проверки заблокированы.
- Не деплоить, не публиковать игру, не отправлять код на внешний сервер без отдельного разрешения владельца.

Приоритеты: P0 — играбельная кампания, управление, честные коллизии, стабильность, все боссы; P1 — качественные оригинальные ассеты, музыка, UI, доступность, таблица рекордов, тренировочный режим; P2 — необязательные CRT, дополнительные эффекты и украшения меню. Для v1.0 обязательны P0 и P1.

# 1. Видение и игровой опыт

## 1.1 High concept

В далёкой колонии человечества обнаружена самовоспроизводящаяся система машин Lattice, способная перестраивать материю живых существ и техники. После аварии она начала поглощать орбитальные станции и планеты. Игрок пилотирует экспериментальный корабль N-07 «Lantern» с автономным магнитоплазменным модулем AEGIS. Задача — проникнуть в восемь заражённых зон, уничтожить сеть управляющих узлов и подавить источник сигнала до его распространения.

Сюжет показывается окружением, короткими радиосообщениями и сменой локаций. Не добавлять длинные катсцены или диалоги, останавливающие игру. Тон: одиночество, технологическая тревога, нарастающая опасность, ощущение путешествия в неизвестность.

## 1.2 Четыре столпа

1. **Позиционирование важнее количества выстрелов.** Уровень — предсказуемая последовательность тактических ситуаций, где нужно видеть безопасный путь.
2. **AEGIS — центральная механика.** Можно закрыться от огня спереди или сзади, запустить модуль в опасную область, отозвать и перенастроить вооружение.
3. **Угроза должна быть читаемой.** Сильные атаки предупреждаются, декорации отличаются от коллизий, хитбокс меньше силуэта, нет внезапной смерти без возможности реакции.
4. **Масштаб и изменчивость.** Враги от мелких дронов до огромных механизмов; каждый этап раскрывает новую пространственную задачу.

# 2. Игровой цикл и состояния

```text
BOOT → TITLE → MAIN MENU → DIFFICULTY → MISSION INTRO
  → STAGE SCROLL → BOSS WARNING → BOSS FIGHT → STAGE CLEAR
  → следующий уровень (1..8) → ENDING → HIGH SCORE → MAIN MENU
                       ↓ смерть
              DEATH → RESPAWN или CONTINUE → GAME OVER
                       ↓ пауза
                     PAUSE → RESUME / RESTART / QUIT
```

Stage Practice запускает только выбранный разблокированный уровень с нормализованным комплектом снаряжения, не записывает рекорд кампании. Разблокировка уровня — при первом начале его в кампании; доступ сохраняется независимо от дальнейшего поражения. Если игрок завершил 8-й уровень, выводятся статистика, финальный экран и титры. Новая игра не переиспользует текущую статистику.

Вход в миссию 2,0 с, название и короткое сообщение. Игрок управляет кораблём в скроллинге и бою с боссом; таймер скроллинга начинает идти после входа. Предупреждение о боссе 3,0 с: корабль управляем, обычные враги и снаряды очищаются, босс входит без опасных атак. Победа над боссом: 2,0 с для анимации, затем экран результата (подтверждение игроком). Пауза останавливает симуляцию, таймеры волн, игровые частицы и звук игрового действия, но не UI. При потере фокуса в активной миссии — автоматическая пауза; возврат фокуса не снимает её автоматически.

# 3. Игровое пространство и технические единицы

## 3.1 Координаты

Базовый viewport **640×360** (16:9). HUD занимает y=0..23 (верх) и y=336..359 (низ). Игровая зона: x=0..639, y=24..335. Ось X вправо, Y вниз. Все размеры и скорости далее в логических пикселях и пикселях/секунду; время в секундах. Центр спрайта — локальный (0,0), если не указано иначе. Центр корабля ограничен x=18..622, y=34..325 и коллизиями с миром. Типичные входы врагов x=672 (справа), x=-32 (слева). Входы внутри экрана допустимы только с визуальным предупреждением либо через заранее видимый эмиттер/портал.

- 1280×720 по умолчанию; fullscreen/windowed, целочисленное масштабирование с letterbox; минимальный размер окна 640×360. При нестандартном соотношении сторон игровая зона не растягивается.
- Вся симуляция на fixed 60 Hz (`_physics_process`). Не привязывать скорость движения/спавн к FPS. При просадке кадров симуляция может догонять до лимита движка, но не ускорять игру через реальное wall-clock время.
- Таймеры, доборы, cooldown и invulnerability измерять в integer ticks; `ticks = round(seconds*60)`; внешние данные могут задавать секунды.
- Визуальный pixel snap применять на рендере, не округлять физическую позицию каждый кадр. Фильтрация nearest, без mipmaps для pixel sprites; alpha без белой каймы.
- Базовый скролл привязан к таймеру этапа `scroll_x = speed * stage_time`. Враги, пули и игрок работают в экранных координатах; привязанные к земле объекты и препятствия имеют мировую X и переводятся в экранную через `screen_x=world_x-scroll_x`. Не применять прокрутку дважды.

## 3.2 Слои и камера

Камера фиксированная. Порядок слоёв снизу вверх: глубокий фон (z=-100), средний (-80), передний декоративный (-60), непрозрачные playfield tiles (-20), подвижные препятствия (-10), предметы (0), враги (10), AEGIS/игрок (20), снаряды (30), опасные предупреждения (35), частицы (40; не перекрывать пули плотным дымом), HUD (CanvasLayer 10), меню (CanvasLayer 20). Тряска — смещение только визуального контейнера игрового мира на 0–3 px, не меняет физику/HUD. Настройка позволяет выключить.

| Действие / InputMap | Клавиатура | Gamepad (Xbox) |
|---|---|---|
| `move_up/down/left/right` | WASD или стрелки | D-pad или Left Stick |
| `fire` | Z / Space (удерживать) | A |
| `charge` | X (удерживать/отпустить) | X |
| `module_toggle` | C | B |
| `module_side` | V | Y |

Все игровые действия переназначаемы, включая клавиатуру и контроллер. Меню имеет фокус и полностью доступно с контроллера. Deadzone стика 0,22; после deadzone движение пропорциональное, диагональ нормализуется (максимальная скорость не увеличивается). При одновременном D-pad и стике предпочтение D-pad; противоположные клавиши взаимно гасятся. События «нажать» для toggle/speed/bomb выполняются один раз, не повторяются при удержании. Удерживаемые fire/charge проверяются каждый fixed tick. При переходах, паузе и смерти заряд сбрасывается без выстрела; после паузы заряд/действия по edge требуют нового нажатия.

## 4.1 N-07 Lantern

Силуэт 48×24 px, вид сбоку, нос вправо. Внутренний hitbox — круг r=5,5 в центре, отображаемый как маленький светлый ромб при настройке Show Hitbox. Контакт корабля с вражеской пулей, врагом или опасным препятствием убивает одним попаданием (Assist имеет один защитный слой на жизнь). Нет инерции: velocity сразу следует input; визуальный наклон ±8° и 3 кадра банковки не влияют на физику. Скорости 105/145/190 px/s; default 145, циклическое переключение 1→2→3→1; переключение доступно в любое время, не привязано к предметам. Spawn x=96, y=180 или безопасная точка из профиля уровня. Базовый корабль всегда достаточен для прохождения без опциональных модулей, кроме учебного получения AEGIS перед основной игрой; обязательные в бою проверки никогда не требуют случайного дропа.

Стандартная стрельба из точки (+23,0); charge muzzle там же. Запрещена стрельба во время death, transition и при отсутствии игрока. При respawn стрельба разрешена сразу, управление — после анимации появления 0,3 с. Двигатель и небольшой ионный шлейф меняют интенсивность при движении, но не скрывают хитбокс.

# 5. Вооружение, AEGIS и улучшения

## 5.1 Оружие корабля (P0)

| Оружие | Цикл | Урон / попадание | Скорость / размер | Правило |
|---|---:|---:|---|---|
| Pulse | 0,15 s (9 ticks) | 2 | 420; 9×3 | первый выстрел мгновенно, удержание автоматическое |
| Charge weak | 0,20–0,74 s | 8 | 365; capsule 16×8 | до 2 уникальных целей |
| Charge medium | 0,75–1,59 s | 24 | 340; capsule 28×16 | до 3 уникальных целей |
| Charge full | ≥1,60 s | 56 | 310; capsule 46×24 | до 5 уникальных целей |

При удержании charge >0,2 s на носу виден шар энергии. Charge capped 1,6 s, хранится до отпускания, без разряда по таймеру. При начале заряда `fire` подавляется сразу (не стрелять до отпускания charge). Отпускание раньше 0,20 s — без выстрела. После выстрела charge cooldown 0,20 s для pulse/charge (поддержать необходимость нового нажатия charge). Заряд не повреждает врагов до выпуска. Если AEGIS спереди, его коллизия не блокирует дружественный выстрел. Terrain останавливает все обычные и заряженные выстрелы; заряженный снаряд наносит урон каждой цели максимум один раз, лимит уменьшается только после фактического повреждения. Закрытая броня считается преградой для Pulse/Charge, но не расходует HP босса. Урон не умножается из-за пересечения двух коллайдеров одной сущности.

В UI шкала 0–100%, деления на 0,75 и 1,6 s; звуковой сигнал на достижении максимума однократно. Максимальный заряд сохраняет постоянный визуальный ореол, без повторяющегося звука. Для доступности опция Toggle Charge: первое нажатие начинает накопление, второе выпускает; клавиша fire не прерывает удерживаемый режим.

## 5.2 Модуль AEGIS

Оригинальный модуль: ромбовидный вращающийся магнитный сердечник, три раздельные броневые пластины вокруг него, светящиеся грани меняют цвет/узор в зависимости от типа вооружения. Размер 32×32, круг shield r=13, damage contact r=10. Без HP. Защищает только от блокируемых пуль, не от стен, лазеров, красной опасной плазмы и контакта корпуса. Сам не получает урон, но отделённый модуль не может пройти сквозь стены. Уничтожение обычных вражеских снарядов модулем не даёт очков. Модуль у игрока с самого начала миссии 1, ранг 1, тип ARC. При смене ранга меняется вид броневых пластин; при смене оружия — узор и цвет.

```text
ATTACHED_FRONT ←──── swap ────→ ATTACHED_REAR
       │ detach                     │ detach
       └──────────→ LAUNCH ←────────┘
                        ↓
                       FREE ── toggle ─→ RETURN ──→ ATTACHED_(desired side)
                          \ terrain hit / lost reachability
                           └────────────────→ RETURN
```

### Состояния и правила

| Состояние | Позиция / движение | Поведение |
|---|---|---|
| ATTACHED_FRONT | корабль +(35,0) | щит спереди, оружие направлено вправо |
| ATTACHED_REAR | корабль +(-35,0) | щит сзади, оружие направлено влево |
| LAUNCH | по направлению от порта, vx ±330, t≤0,35 s | щит активен; контактный урон; не проходит стены |
| FREE | цель: (clamp(player.x + side*160,24,616), player.y); скорость ≤165 | игрок меняет Y через своё движение; базовая независимая стрельба по направлению side |
| RETURN | скорость 420 к порту desiredSide | движется по прямой; щит активен пока не столкнётся со стеной; безопасный fallback |
| SWAP | краткое движение вокруг корабля за 0,20 s | collision shield отключён; пауза огня; сторона меняется атомарно по завершении |

`module_toggle`: attached → launch; launch/free → return; return/swap → игнорировать. `module_side`: attached → SWAP (если порт размещается без стены), detached → сменить desiredSide (FREE сохраняет launchSide для текущего полёта, новое значение используется при возврате), RETURN → обновить целевой порт; SWAP → игнорировать. После начала transition 0,20 s — debounce. Модуль, который ушёл за видимый экран или наткнулся на solid, возвращается. Если RETURN не может достигнуть порта 0,4 s (с момента запуска возврата), он исчезает на 0,15 s без щита и появляется на ближайшей безопасной стороне. При наличии стены с обеих сторон перейти в безопасный stowed-режим: визуально сжать пластины у корпуса, выключить щит/огонь/контакт, автоматически попытаться пристыковаться каждые 6 ticks. Никогда не убивать игрока из-за смены порта, никогда не телепортировать активный щит сквозь стену. Attached при конфликте с solid немедленно stowed. Оба порта могут быть за экраном частично; если центр выходит за x=13..627, порт недоступен. Игрок не является solid для модуля.

AEGIS блокирует `blockable` пули при первом пересечении щита. Entity damage contact: 5 damage каждые 0,20 s на одну цель, cooldown отдельный на entity ID; босс/броня не получают контактный урон, если их зона не уязвима. Следующая цель независима; не допускается бесконечное накопление map записей после смерти сущностей. Обычная пуля с shield hit и ship hit в одном tick должна исчезнуть до проверки корабля, если траектория раньше пересекла shield; при обратном порядке попадание в корабль засчитывается. См. раздел 14.

# 6. Жизни, сложность, чекпоинты, рекорды

## 6.1 Смерть и восстановление

Arcade: 3 жизни (включая текущую), бомба 1, AEGIS ARC1, скорость 2. При смертельном столкновении: life--, звук + взрыв 0,65 s, мир/таймер замораживаются (частицы death работают), затем сброс к последнему checkpoint. Очищаются все враги, пули, предметы, hazards, временные эффекты и HP босса. Состояние этапа реконструируется из данных checkpoint, не serializing сцены. Чекпоинты t=0,40,80,120 (последний — прямо перед входом босса). Если игрок умирает на t=39,99, возврат на 0; при t>=40 после фиксации checkpoint — на 40. Если умер в бою, босс заново с полным HP. Checkpoint фиксируется перед collision step при достижении tick. При смерти на границе последнего тика скроллинга безопаснее перейти в boss intro только при живом игроке; на t=120 checkpoint уже действителен.

Возврат: AEGIS текущего типа, rank -1 минимум 1, `bit=max(0,bit-1)`, ракеты rank -1 минимум 0, не восстанавливать потраченные бомбы, минимум 0; набор после смерти становится текущим и переносится между уровнями. AEGIS всегда available даже после потери всех улучшений. Скорость сохраняется. При respawn 2,0 s невосприимчивость к пулям и контакту с врагом, 0,3 s появление; solid всегда опасен. В течение 2 s мигание alpha 0,45..1 не быстрее 3 Hz; не исчезать полностью. Если выбранная точка не безопасна, вычислить midpoint коридора у x=96, при необходимости fallback scan x=48..160 с шагом 4 и y=40..320 с шагом 4, выбрать ближайшую к (96,180) безопасную точку. Валидатор должен запрещать checkpoints без безопасной точки с радиусом запаса 20 px. Начиная с checkpoint, события строго `event_tick >= checkpoint_tick`; события до него пропускаются, не спавнятся догоняюще. Геометрия вычисляется с текущим scroll_x, не начального уровня.

Игра не позволяет фармить одни и те же очки после смерти: при checkpoint сохранить score; при откате score восстановить к checkpoint, но **жизни, бомбы и снаряжение не откатываются**. Дополнительные жизни за score milestones 50k и 120k могут быть получены только один раз на run; их persistent run flags не откатывать. При checkpoint сохраняется только score и локальная статистика, не persistent flags. Pickup life из скроллинга — идентификатор события/носителя, выдаётся один раз на run; после отката повтор заменяется +0 и не спавнится. Очки за уничтожение врагов пересчитываются при повторном участке.

## 6.3 Счёт

Очки enemy/boss по таблицам; уничтожение составного босса: бонус только за финальное ядро + явно указанные destructible parts. Предметы по 100 за сбор, плюс cap-бонус, если применим. Имя до 8 ASCII chars A–Z/0–9/space; fallback PILOT. Очки целочисленные 64-bit. Ending/score запись однократна; двойной accept не создаёт duplicate. Не использовать реальный elapsed time для gameplay scoring.

# 9. Уровни: общий формат и сценарный контракт

## 9.1 Геометрия

Кампания использует 8 stage data resources. Данные можно хранить в `.json` (UTF-8), валидировать перед запуском, затем загрузить в typed resources. Уровни не строятся произвольно в runtime. Для компактности GDD описывает сплошные потолок/пол через piecewise-linear профили.

Профиль `(t, top, bottom)` задаёт верхнюю и нижнюю границы свободного коридора у **правого края** в момент t: узел хранится при `world_x = speed*t + 640`. Для любого world_x вычислить `q=(world_x-640)/speed` и линейно интерполировать top/bottom между узлами; вне диапазона clamp first/last. Верхняя solid область y=24..top, нижняя bottom..335. Границы top=24/bottom=336 означают открытый край. Генерировать render tiles и collision полилинию из одних и тех же данных, sample каждые 8 px world X, линейно между семплами; исключать нулевые толщины. На shader/background не возлагать коллизии. Участки сплошного коридора должны быть не уже 100 px, а между подвижными hazards — существовать путь шириной минимум 48 px. Декор walls может выступать не более 2 px за collision; опасный край контрастный.

При t=0 видимый участок соответствуют q от -640/speed до 0. Большинство уровней имеют открытый профиль в начале и конце. С t≥108 у правого края полностью открытый профиль, к boss warning поле гарантированно открыто (при speed≥64 px/s). Boss arena не имеет scroll terrain. В boss warning удалить scrolling hazards, frozen background может продолжать медленную декоративную прокрутку (без коллизий).

## 9.2 Spawn DSL (норматив)

Каждая строка: `t | enemy_ID | entry | y | count | gap | variant/drop`. t — начало спавна, gap в s, count сущностей, каждая в t+i*gap. Entry `R` x=672, `L` x=-32, `T`/`B` world-mount в колонке x=672 (вычислить wall y в этой world_x; center на 13 px внутрь corridor от boundary; при open edge на y=40/320 с видимым отдельным металлическим кронштейном). Для E07 L/R подход к staging x=80/560 соответственно со скоростью 180, затем warning и dash на противоположную сторону; направление атаки для L вправо. E11 L → вправо, R → влево. Для остальных mobile L запрещён кроме E07/E11. `y` может быть одиночным числом (все одинаково), списком `[a,b,...]` циклически или `alt(a,b)`; `corr(P)` — доля свободного пространства у entry X: `top + P*(bottom-top)` с clamp запасом 20 px. Если указано числовое y, и при спавне оно пересекает terrain, зажать y в коридор с запасом размера hitbox+8. Весь дальнейший путь не автоматически clamp (кроме E07 lock y, E16 bounce); геометрию и движение надо плейтестить. Для `T/B` y=`-` (расчёт автоматически), стреляет из видимой части.

`variant` — `UP`/`DOWN` для E16, phase offset для sinus если указан (по умолчанию 0), `drop=arc/prism/ember/...` для E05; все E05 обязательно имеют drop. `PICKUP` — появляется непосредственно на x=600 в момент t; y из строки, count=1. Все события фиксированы, а не генерируются случайными шансами; `event_id=stage_index:row_index:subindex`. Табличные события ниже — обязательные стартовые сценарии, допускается менять balance только с отчётом. Если несколько событий на одном tick, обрабатывать в порядке строк. В конце уровней последний spawn должен успеть выйти/быть очищен в boss warning.

## 9.3 Движущиеся препятствия (hazard DSL)

`worldRect(t, y, w, h)` — world center X=speed*t+640, постоянный y, rect solid (появляется с правого края около t; движется влево со scroll). `oscRect(..., A, period, phase)` — y(tNow)=y+A*sin(2π*(tNow-t)/period+phase) начиная с stage time, даже после checkpoint; это deterministic geometry, не одноразовый spawn. Столкновение с любым solid смертельно, независимо от обычных i-frames. Отрисовка/телеграф опасного moving solid минимум 0,8 s перед входом в игровую область при возможности: полоски на правом краю и стрелки движения; предупреждение не коллидирует. `gate(t,w,gapY,gapH, A, period)` — vertical world slab width w, две solid rect от верхнего/нижнего края игрового поля до щели, центр щели oscillates A (A=0 fixed), полная высота gapH. Не создавать overlap ни между движущимися solid, ни с terrain, который сужает доступный зазор ниже 48 px. Геометрия eval из absolute t, для checkpoints reconstruction deterministic. Стены/препятствия не наносят урон AEGIS, но блокируют shield/выстрелы. “Декоративная” анимация не solid. У всех hazards уникальный id. `pulseBeam` hazards в уровнях описаны отдельно по временам; если checkpoint позже времени warn, уже начатые timed attacks не восстанавливать (за исключением геометрии). Игрок не может вылететь из playable bounds.

# 10. Кампания: восемь уровней

# 11. Боссы: точные боевые сценарии

## 11.1 Единый контракт боёв

Arena открыта, root boss по умолчанию center (540,180), sprite layers могут выступать до x=639. Boss intro 3 s: x движется 760→540 за 2,3 s (ease out), затем 0,7 s idle; коллизии/урон boss и damageability выключены до завершения warning. В бою коллайдеры boss — только указанные зоны; визуальный декор без попаданий явно отделяется от solid body. Игрок получает урон при контакте с любой активной body/armor zone. `core` и `part` hitboxes — окружности или прямоугольники; они также body, если не помечено иначе. HP босса — сумма HP фаз/частей для HUD; части с независимым HP видны отдельными сегментами. HP не восстанавливается между attack loops. Все weak points светятся при уязвимости (outline 2 px), закрытые — затемнены бронёй с крестовым рельефом. Все phase transitions immediate после depletion, 1,2 s intermission: boss invulnerable, удалить hostile bullets/hazards boss, не удалять дружественные снаряды, сбросить attack timer. Во время intermission физические body collisions активны. При финальной смерти коллизии сразу выключаются и все hostile hazards удаляются. Награда начисляется один раз.

У каждого этапа собственный `phase_elapsed` в fixed ticks. Расписание циклов задаёт start times относительно начала фазы/цикла. Если паттерн включает warning, начало — предупреждение, сама атака после warning. Повтор цикла с момента t=cycle seconds независимо от предыдущих пуль. Когда у игрока временная invulnerability, босс продолжает паттерн (кроме death/pause). Hypothetical DPS Pulse alone=13,33, full charge approximately 31,11 dmg/s при постоянной цели; планировать battle duration 30–70 s с реальным уклонением, не делать time limit. Ни один босс не требует конкретного элемента оружия, жизни или бомбы. Нет гарантированных обязательных задних попаданий: все weak points хотя бы периодически доступны слева. Для boss part определить `damage_group_id`: урон одному group максимум один раз на снаряд. При body overlap приоритет weakpoint перед armor только если weakpoint ближе по swept ray либо физически на front; размеры armor rectangles исключают weakpoint face. Использовать отверстия в armor, не просто весь спрайт как box.

Общие shorthand: `FAN(k, s, v)` = AIM(k, half-angle s, speed v); `RING(k,v,phase)` как в 8. `core` и offsets указаны относительно boss root, обычно muzzle x=core.x−radius или boss root−52. `at t` — момент события. В каждой фазе первой опасной атаке предшествует минимум 0,7 s. В расписании обычных FAN/RING/STRAIGHT/CAGE время t — начало предупреждения; выстрел после 0,30 s (если явно задан иной момент, follow explicit timing). Normal warning marker: 0,30 s для направленного залпа, 0,9–1,2 s для лазера/крупного hazard. Aim фиксировать при warning, не при fire. Bullet ring из видимого emitter в боссе; центр emitter должен быть визуально понятен. Снос опасности бомбой не прекращает сам attack clock. При объявленных «окнах» таймер периодического огня остаётся синхронизирован, если vulnerability closed. Core закрыто физической заслонкой на его лице (не отдельный damageable part).

## 11.2 Защита от softlock и балансовые цели

- На всех difficulty можно убить все boss phases только Pulse (без AEGIS, charge, bomb); автоматический damage test с циклическими окнами проверяет достижимость target, но не заменяет ручной бой.
- Если игрок долго не стреляет, бой не завершать автоматически; атаки повторяются без расширения hitbox, накопления hazards и без поэтапного увеличения скорости.
- Если паттерн вызывает entity cap, пропустить низкоприоритетный spawn с debug log, не заменять внезапным unblockable. В normal campaign cap не должен достигаться.
- Вручную проверить как минимум low-loadout Arcade, high-loadout Arcade и Veteran на каждом боссе; Assist single shield должен корректно восстанавливаться после жизни. Начальный ориентир: медианная дуэль 35–60 s для подготовленного игрока, финал 50–90 s; это цель, а не гарантия до playtest.

# 12. Art Bible — графика, визуальное качество, производственный pipeline

## 12.1 Художественное направление

Ретро-футуризм конца 1980-х / начала 1990-х с современным качеством пиксельного искусства. Не имитировать конкретные оригинальные спрайты. Механика и органика объединены на уровне материалов: керамика, тёмный металл, бронированные волокна, кристаллические полупрозрачные детали, светящиеся цепи. Стиль — ручной pixel art с чёткими силуэтами, малым количеством цветов на объект, читаемыми деталями. Не использовать случайные SVG-треугольники и один и тот же корабль в перекрашенных вариантах. Не применять фотографические текстуры, гладкий векторный минимализм в игровом мире, общий neon glow вместо объёмной пиксельной кластеризации.

## 12.4 Как создать оригинальные ресурсы силами агента

Инструменты: Python 3 + Pillow (установить только dev dependency), SVG source optional для логотипа/панелей, затем rasterize до base pixels; Godot не должен зависеть от Python для запуска. Допустимы вручную созданные PNG с editable sources. Если нет художника/генерации изображений, реализовать authored procedural pixel art: рисовать каждый enemy и boss отдельно через слоистые polygons/lines/ellipses с конкретными координатами, material ramps и micro-detail, не через один универсальный blob algorithm.

Алгоритм для каждого оригинального sprite set:

1. Создать прозрачный base cell, определить silhouette через набор целочисленных vertices и видимых частей. Для N-07 использовать контур из 12.2; для остальных — конкретные silhouette briefs выше. Сначала силуэт чёрной маской, проверить 1×.
2. Нанести тёмную кромку, внутренний базовый material, затем 2–4 tone ramps отдельных панелей (light upper left, shadows lower right). Cockpit/cores separate masked layers. Использовать nearest и integer coordinate drawing, без bilinear blur или smooth gradient на маленьком спрайте.
3. Добавить 3–8 authored pixel clusters панели, винты, fins, vents, silhouette asymmetry; не рассыпать noise по всему спрайту. В organic вариантах ветвящиеся curves аппроксимировать несколькими пиксельными полигонами; избегать random noise как основного материала.
4. Разнести подвижные детали, создать кадры по curated poses, не генерировать каждый кадр независимо. Pivot, body size, emission anchor неизменны. Можно применять palette swap только для состояний и материала, не вместо уникального дизайна.
5. Собрать atlas и metadata с источником, pivot, cell, frame_count, fps, `sha256`. Проверить expected image bounds и transparent margin. Сформировать contact sheet всех player, enemies, boss silhouettes, pickups, tiles и sample screenshot каждого stage. Финальные ресурсы просматривает человек: если спрайты выглядят как прототип из геометрических фигур, добавить детализацию до релизного уровня.
6. Генерировать background: fixed seeded star placement, authored polygons distant structures, parallax layers; noise low contrast только внутри material masks. Сделать реальные seamless seams, избегать bright enemy-like pixels в ближнем декоре. Туман ограничить background-only.

Команда сборки ресурсов (реализовать, а не предполагать существующей): `python tools/build_art.py --seed 47021 --output assets/`; до/после — manifest hashes. Не перезаписывать hand-authored assets без `--force`. Все font/license files включить. В production ship PNG/OGG/WAV уже committed. Никаких внешних генеративных сервисов, платных зависимостей или скачиваний при запуске. Если владелец позже предоставит профессиональные спрайты — менять через ArtRegistry, не переписывать physics.

# 13. Audio Bible — музыка, эффекты, микс и создание звука

## 13.1 Музыкальное направление

Оригинальный soundtrack: dark melodic synthwave + FM/16-bit arcade + industrial percussion; мелодии с лёгкой тревожностью и запоминающимися темами. Не использовать мелодии, сэмплы и аранжировки R-Type или узнаваемые чужие треки. Ритм должен поддерживать игру, а не утомлять. Никаких vocals. Крупные атаки босса не зависят от BPM: музыка может быть paused/resumed сама, gameplay deterministic отдельно.

Музыка — 48 kHz stereo, OGG Vorbis качеством примерно q5–6 (или lossless WAV для source), runtime loop region sample-aligned. SFX — 48 kHz mono WAV PCM16 для positional/панорамируемых эффектов, stereo только для особых stingers/ambience. Пик каждого сэмпла ≤−2 dBFS, короткие fade in/out 2–10 ms где нужны, никаких clicks. Проверка файлов: duration >0, sample rate, non-silent RMS, no clipping, loop boundaries. Loop music не должна завершаться пустой паузой. Не обрезать reverb tail без wrap/overlap.

## 13.3 Generation recipe: оригинальная музыка без платных инструментов

Реализовать `tools/build_music.py` (Python 3, NumPy + stdlib `wave`; FFmpeg optional offline conversion to Vorbis, fallback WAV runtime), либо создать MIDI `.mid` + offline synth, сохранив собственные editable note-event sequences. Все ноты/партии оригинальные. Вход: table track metadata and authored melodic variations, seed 47021+trackIndex. Runtime не синтезирует всю музыку в реальном времени. Генератор обязан собрать всю таблицу треков, а не один loop с разными BPM.

Пример авторской главной темы (degrees натурального минорного лада, `1=root`; менять 7 на harmonic leading tone только над major dominant): четыре такта, каждый 8 eighth-note slots; `-` означает продолжение предыдущей ноты, `r` rest. Motif A: `1 - 3 5 6 - 5 r | 3 - 2 1 2 - 3 r | 4 - 6 5 4 3 2 r | 5 - 7 1' 7 - 5 r`. Motif B: `1' - 7 6 5 - 3 r | 6 - 5 3 2 - 1 r | 4 5 6 - 4 - 2 r | 5 - 7 5 3 2 1 r`. Это исходный мотив для title и T01/T08/B08, остальные треки используют собственные note sequences. Для остальных подобрать отдельные 4-bar A/B phrases, следующие профили ритма и degree patterns (r = rest, - = sustain; bars разделены `|`, восемь slots):

not only transpose identical full arrangement):
B01 1 1 r 2 1 r 5 r | 2 2 r 6 2 r 3 r | 1 r 5 r 3 r 2 r | 5 7 r 5 2 r 5 r

Для T02..T07 и B01..B07 phrase B: первые 2 такта повторяют A с заменой каждой второй не-rest ноты ближайшей chord tone выше; последние 2 такта descending response от ближайшей к текущему верхнему тону ступени вниз, ending на 5 или 1; сохранить исходный ритм, последняя eighth rest. Включить явные MIDI/event lists в исходник, не генерировать произвольные новые мелодии на каждом запуске. Для M01 и M03 — упрощённая половинная плотность собственной темы, M02 — variation главной темы в D major. Инструменты различаются по дорожкам, даже если строятся общими synth functions.

Arrangement на каждые 16 bars: bars 1–4 intro bass+pad, 5–8 drums+arp+A, 9–12 full lead+B, 13–16 breakdown/turnaround, на следующем блоке добавить variation rhythm/countermelody; последние 4 bars clean transition к bar1 без тишины. Для title/menu снизить ударные и lead density, боссы начинают с bass+drums сразу, motif entry bar2. Grid 1/16 с deterministic humanize ≤3 ms только для перкуссии; не менять BPM. Вокал отсутствует.

Synth specification (source samples 48k):
- Kick: sine sweep 135→45 Hz over 85 ms, decay 0,18 s, optional initial click lowpass; hats filtered white noise HP 6 kHz 0,04–0,12 s; snare bandpassed noise 1–4 kHz + sine 165 Hz decay 0,12 s; tom sine 140→75 Hz 0,22 s. Все оригинальные synthesized, без copyrighted samples.
- Bass: band-limited saw + sub sine, attack 5 ms, decay 90 ms, sustain 0,65, release 45 ms, lowpass ~1,2 kHz, eighth/16th note patterns. Use chord root, fifth, octave. Защита от aliasing: sum harmonics only below Nyquist.
- Lead: two-op FM `sin(2πf t + I sin(2πr f t))`, ratio r=2 or 3, index 0,8–2,0 decay; ADSR 8/100/0,55/80 ms, delay 1/8 beat feedback 0,18 stereo. Glass track bell shorter sustain, industrial track saw/chip layer. Pads 3 voices detune ±4 cents, sine/triangle mix, attack 150 ms release 250 ms, slow filter modulation. Arp 1/8 or 1/16, chord tones, amp decay 70 ms.
- Stereo pan: kick/bass/lead center, arp ±0,25 alternating, pads ±0,35; equal power. Render blocks/track memory <=256MB per process or chunked; mix float32; apply mild limiter / normalize target music peak -2 dBFS and integrated approximate RMS dynamic range (avoid overcompression), target perceived loudness consistent. Wrap effect tails from end to beginning then verify discontinuity near loop; start/end zero-crossing or crossfade <=20 ms preserving exact loop length.
- Export track source, note events JSON/MIDI and OGG/WAV; use ffmpeg `-c:a libvorbis -q:a 5` when available, verify playback via Godot and actual loop. Use no external copyrighted samples or recordings. Test actual audible quality with human listeners if possible; if synthetic demo-like, refine motifs/instrument arrangements, not mark final quality solely from sample-rate checks.

## 14.3 Runtime responsibilities

- `GameState`: pure run values (`stage_id`, difficulty, `lives`, score, credits, equipped types, ranks, milestone flags, run qualification, stage death counts). Single owner. Signals `run_started`, `state_changed`, `score_changed`, `loadout_changed`; no duplicate sources of truth. No direct UI scene refs in autoload.
- `MissionController`: FSM `INTRO/SCROLL/WARNING/BOSS/DEATH/RESPAWN/CLEAR/PAUSED`; owns fixed tick order. Transition guarded against duplicate calls. Spawn player and HUD; no `await` timers for gameplay that survive scene unload. Death handler once per tick; phase change and death order explicit below.
- `StageDirector`: sorted expanded timeline; pointer to next event; `reset(tick)` binary-search; computes scroll offset + render update; boss trigger at tick7200; maintains stable event IDs. Spawned event cannot fire twice in same section attempt.
- `TerrainProfile`: `top_at(world_x)`, `bottom_at(world_x)`, `swept_hit(segment,radius)`; moving solid list eval absolute stage ticks. Rendering uses same geometry. Clip beams at first intersected solid. Separate decorative renderer.
- `PlayerController`: input snapshot, movement, shooting cooldown/charge and hit state. Queries mission for permitted actions. AEGIS FSM manages docking positions and turret fire. EnemyActor uses shared archetype config + distinct state machine behavior; no independent frame-time timer.
- `ProjectileSystem`: pooled typed arrays or lightweight objects with spatial buckets, stable int IDs, prev/curr, owner, team, damage, hit_groups, expiry, flags. Ray/capsule sweep for fast bullets and moving player/AEGIS targets; avoid naive discrete Area2D-only for 420 px/s small bullets. Dedicated render (draw textured quads or pooled Sprite2D) from same simulation data. Visual nodes never own damage.
- `DamageResolver`: central function one hit/target/tick per appropriate weapon semantics, immunity and shield priority; queued deaths with one-time reward; no recursion that creates twice-destroyed child. Stable ordering by event time-of-impact and entity ID. `PatternLibrary` pure functions returning bullet/beam descriptors, no node references, angle convention +X=0°, down=90°.
- `BossActor`: phase index/HP array, object shape ownership, schedule attack callbacks using ticks, phase state, vuln windows; phase-aware `damage_group_id`, emit oriented telegraph. Never wait on cleared hazards to advance after HP depleted. UI derives boss total from active data only.
- `AudioManager`: events receive `(sfx_id, screen_x, priority)`; no gameplay outcomes depend on audio. Pause cancels looping charge and stores music playback; clear pools by bus on scene unload.
- `SaveService`: settings/progression/high scores only, atomic temp rename and recovery, separate schema version. No mid-run save/resume in v1.0. Always test under temp user directory/headless; do not overwrite user real scores in automated tests.

## 14.4 Simulation order / collisions

All in one tick (or measured consistent equivalent), physics independent from frame render. Stage tick `0` first tick on SCROLL (spawn events tick0, if any); after tick 7199 -> boss warning, checkpoint7200. If player death on last tick, use actual checkpoint previously fixed; if stage t7200 reached before collision handling, checkpoint boss. Prevent double-advance; simplify by defining final stage tick 7200 as transition-only (no damage, no spawns). Inputs sampled once. Keep paused/intro outside active simulation loops except visual state.

```text
1. Snapshot input, process pause/quit guards.
2. Advance stage clock; set reached checkpoint and snapshot pre-wave score.
3. Expand due events; eval terrain at previous/current absolute tick.
4. Update player and AEGIS positions; handle fire/charge/bomb request.
5. Update enemies/boss, schedule attacks; create due projectiles/hazards.
6. Move existing/new projectiles (new one moves next tick), update hazard shapes.
7. Collect collision candidates via spatial hash + swept segment tests;
   sort by (time of impact, tie priority, stable entity IDs).
8. Resolve friendly projectile -> nearest terrain/armor/weakpoints, reflect/pierce;
   resolve hostile projectile -> solid/shield/bit/player; resolve player body/terrain/hazard.
9. Resolve bomb impulse (if due this tick before lethal hostile damage; still terrain wins),
   damage/deaths exactly once, child spawns, drops, score changes.
10. Resolve fatal player state first if simultaneous with non-final stage transition;
    if final boss death & player death same tick, player death takes precedence, rollback checkpoint score,
    no victory bonus; remove phases/hazards only on surviving player progression.
11. Cleanup expired/offscreen/dead, flush signals and visual/audio events, update HUD.
```

Implementation clarification: step 8 queues candidates/damage (not irreversible player death), step 9 bomb deletion/damage and sorted resolution; determine physical terrain at actual sweep. If bomb active, ordinary hostile bullet candidates removed (bomb already took effect) and i-frames apply; terrain/crush remains fatal regardless. Newly spawned projectile has prev=curr and can hurt on overlap except protected by emission-distance rule; movement next tick. Boss part death may disable later queued attacks/damage to the part; transitions occur after collision processing to avoid double phase advancement.

Collision requirements:
- Player vs solid = lethal (unless temporarily absent during death animation), not physics bounce. Swept circle/terrain handles small thin wall. Use relative movement for moving hazard/player and projectiles vs moving player/shield. Use segment-to-expanded AABB or segment-to-circle for circle; capsule approximated by union/exact sweep of shape, not by extending in all directions by visual sprite width. The full charge capsule's long axis follows velocity. Terrain normals needed for PRISM reflection, offset 0,5 px along normal, consume remaining path in tick (cap 3 intersections per tick). Prevent corner double-reflection bugs. Bullet passes through destroyed target only if that bullet has remaining unique-hit budget; no repeated damage on next tick.
- AEGIS vs hostile shield: tie priority terrain → shield/bit → ship if contacts identical TOI; unblockable ignores shield. Player takes hazard/solid precedence regardless of invulnerability. Body collision of armed enemies with player always separate from module (cannot eliminate contact retroactively when both TOI identical; player damage if body touched at same instant). Sort collision events by stable entity ID; no iteration order from hash dict as gameplay source of nondeterminism.
- Damage rounded to integers; difficulty multiplies HP once at spawn (ceil); bullet speed once at spawn; no nonlinear scaling with time. Hit cooldown per entity ID + current run/reset scope. On scene transition clear pools, audio loops, collision records. No signals from freed nodes.
- Collision categories logical: `PLAYER`, `FRIENDLY_SHOT`, `HOSTILE_SHOT`, `ENEMY_BODY`, `ENEMY_WEAK`, `ARMOR`, `TERRAIN`, `HAZARD`, `AEGIS_SHIELD`, `BIT_SHIELD`, `PICKUP`. If using physical layers, assign 1..12 in that order, but use swept pipeline as source of truth; do not let Area2D callbacks duplicate damage. Debug draw hitbox and past path separately.

## 14.6 Data schema / validation

Top-level data includes `schema_version:1`. Each ID unique and referentially valid; finite numbers; valid integer count/cooldown; `start_tick+gap*(count-1)<7200`; stage count exactly8; boss exists; checkpoint tick exactly specified; terrain nodes strictly increasing; top<bottom, available gap; damage/hitbox dimensions fit sprite with documented exceptions; no unsupported `variant`; paths exist exact case (Linux); audio duration/frame indices non-negative; expected stage asset count. Validate arrays are sorted with ties stable. Unknown gameplay data keys fail validation (except documented optional metadata). Retain all events/hazards with stable names. Failed data load should show explicit human-readable error in development (exit code !=0 in test), not silent default substitution. Production build must pass full manifest checks.

Define boss JSON fields: `id`, `sprite_id`, `root_motion` (center, sin amplitude, period), `armor_shapes[]` (`id`, type, offset, size/radius, phases), `phases[]` (`id`, `parts[]` with hp/offset/radius, `cycle_ticks`, `open_intervals_ticks`, `events[]` with `at_tick`, `pattern`, `warning_ticks`, `emitter`, typed params; optional `requires_part`, `minion_cap`), `score`, `part_scores`. Beam x defaults to muzzle x, only use fixed x when specified. Phase loops use half-open intervals `[start,end)`; use seconds with decimal point in data, convert to fixed ticks. Например `[0; 4.8)` — от 0 до 4,8 секунды, не включая конечный тик. В формулах BEAM с десятичными запятыми трактовать параметры в порядке y, width, warning, active, x0; при переносе в JSON использовать десятичные точки. Boss phases with multiple part HP require all parts dead, never use an aggregate HP threshold that can skip remaining part. Pickups/death/score state serialized only in run object (not persistent file).

Automated path safety test: sample stage geometry at 60Hz or conservative grid (e.g. dx=8,dy=4, dt=1/30), model player's max speed190, solid expand by r=5,5+4 margin. Dynamic programming/reachability from x96 checkpoint safe start through each interval with movement budget; test both static/moving geometry. Treat beams/arms as additional time-varying obstacles in targeted tests. This proves only geometric reachability under simplified assumptions, not gameplay fairness. Use real playtests for bullet pressure. Compare generated collision shapes to visual outline via debug snapshots. Check min boss windows and minimum travel time to avoid impossible beam at speed1 (speed switch accessible). No cheats/no-damage in manual acceptance recording.

## 17.2 Manual playtest checklist

At least one complete Arcade playthrough with stage owner or qualified tester, using keyboard or gamepad; if no human available, explicitly state "manual playthrough not verified", do not claim full acceptance. Each level additionally start from checkpoint via practice/debug harness and observe active gameplay (not only headless). Verify:

- At 1×/2×/fullscreen sizes, all terrain boundaries, enemy bullets, weak points, charge, module side are readable and never covered by HUD; all eight stages visually distinct; no debug graphics or text placeholders in release.
- Player moves instantly, diagonal equal speed, input feels responsive; controller hotplug/focus loss behaves sensibly; rebound/resume requires correct new input.
- Front vs rear shielding necessary in some encounters but not single mandatory upgrade; no unavoidable shot from edge, laser telegraph clearly visible, enough time to react. Check staying at speed1 and ability to speed-cycle.
- Test B01..B08 with base and upgraded loadouts. Log time to kill, deaths, frustrating moments, specific coordinates/ticks. Achievable without spending bomb on mandatory gate; damage windows visibly sync. End boss no arbitrary invulnerability lock.
- Check checkpoint after every stage death (including mid-boss), no duplicate score farming, no missing guaranteed AEGIS, no item lost to wrong geometry. Test respawn on 40/80 while obstacle on screen.
- Music unique for each stage/boss, no silence/seams/clicks during normal loop, warning audible over max firing, menu and settings volumes correct at 0/50/100, no clipped sound, SFX not irritating at held fire. Human quality review of original music/visual assets mandatory before calling them final.
- Test settings persist after restart, corrupt save fallback without destructive changes, score qualifies correctly, continue not eligible, stage practice unlocks, credits/ending/menu return.
- 30-minute stress/soak on target-like Linux, manual resize/alt-tab/window close; Windows executable launch, input and audio if environment supports it. Record build hash, engine version, platform, FPS p50/p95 (record frame ms rather than misleading FPS percentile), physics p95, memory trend. Do not claim benchmark without measuring.

## 17.3 Release requirements

P0/P1 all delivered, all 8 full levels playable, no known crash, input lock, checkpoint softlock, collision tunneling, loss of profile, missing asset, endless music bug, duplicated score, or unmarked dangerous geometry. All automated tests pass; QA report lists known minor bugs and intentional deviations. Art contact sheets and gameplay screenshots available in docs (not just title preview). Build scripts validated in clean checkout with pre-generated assets, Godot import works offline. Linux and Windows separate release exports (verify actual exported executable; if Windows unavailable, explicitly distinguish untested export from ready). `README` includes controls, setup and build commands, tested Godot version, system requirements, source art/audio regeneration. No placeholder TODO blocking functionality. Release owner approval required for publish; no deploy/push implied by this GDD.

Suggested commands from repo root (paths implement):

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r tools/requirements-dev.txt
python tools/validate_content.py
# Asset regeneration only when updating art/audio, not required to run a clean release:
python tools/build_art.py --seed 47021 --output assets/
python tools/build_sfx.py --seed 47021 --output assets/audio/sfx/
python tools/build_music.py --seed 47021 --output assets/audio/music/
godot --headless --path . --editor --import --quit
godot --headless --path . --script tests/run_all.gd
godot --path .
# With matching export templates and presets installed:
mkdir -p dist/linux dist/windows
godot --headless --path . --export-release "Linux" dist/linux/VoidLantern.x86_64
godot --headless --path . --export-release "Windows" dist/windows/VoidLantern.exe
```

Do not claim these commands passed until implementing repo and running them. `pip install` and installing Godot/templates may require network initially; gameplay and build from pre-provisioned toolchain/assets must not require network.
